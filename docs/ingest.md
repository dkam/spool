# Inbound mail

`Ingest::Inbound.ingest(raw, source: nil)` takes raw RFC822 bytes and returns a
`Result` with `outcome` of `:created`, `:duplicate` or `:rejected`.

That signature is the whole design. Everything that delivers mail — the IMAP
poller, a provider webhook, a test fixture, a console paste — calls this one
method with bytes. Nothing upstream of it knows anything about tickets.

```
raw bytes
   │
   ├─ LoopGuard.reject_reason        → :rejected, nothing created
   ├─ message_id_for                 → :duplicate if already stored
   │
   ├─ MimeSplitter                   headers / text / html / attachments
   ├─ Customer.find_or_create_by_email!
   ├─ Threader.find_ticket           → existing Ticket, or a new one
   ├─ Message.create!                blobs compressed on write
   ├─ Attachment.store! ×N           deduped by sha256
   └─ ticket.record_inbound_activity!  → state: open, last_activity_at
```

## Order of work, and why

**Rejection comes first, before anything is created.** The failure mode this
prevents is the classic one: Spool replies to an out-of-office, whose sender
replies to that, forever, with a new ticket each round. A rejection that happens
after `Customer.create!` still leaves debris.

## Rejection rules (`Ingest::LoopGuard`)

| Rule | Signal |
| --- | --- |
| `auto_submitted` | RFC 3834 `Auto-Submitted:` anything other than `no` |
| `precedence` | `Precedence:` of `bulk`, `list`, `junk`, `auto_reply` |
| `suppression_header` | `X-Auto-Response-Suppress`, `X-Autoreply`, `X-Autorespond`, `X-Autogenerated` |
| `mailing_list` | `List-Id`, `List-Unsubscribe`, `List-Post` |
| `bounce` | `Return-Path: <>`, or a `multipart/report; report-type=delivery-status` body |
| `robot_sender` | Local part is `mailer-daemon`, `postmaster`, `no-reply`, `bounces`, … |
| `self_sent` | The `Message-ID` matches an existing **outbound** message |

`self_sent` is exact rather than heuristic, and it matters because the `From:`
header on outbound mail stays `support@` so that replies land back in the
support mailbox — which means a Bcc or a list echo can deliver Spool's own
message straight back to it.

Every rejection is logged with its reason. Nothing is stored.

## Idempotency

Both retry paths — an IMAP re-poll, a provider redelivery — can deliver the same
message twice. The unique index on `messages.message_id` is the guarantee;
`Ingest::Inbound` does a cheap pre-check to avoid the parse-compress-write work,
and rescues `ActiveRecord::RecordNotUnique` for the case where two workers race.

**Mail without a `Message-ID` exists.** Spool synthesises
`<sha256-…@spool.invalid>` from a hash of the raw bytes, because a content hash
is the only choice that still deduplicates a redelivery of the same message — a
random id would turn every retry into a new ticket. `.invalid` is reserved by
RFC 2606 precisely so it can never collide with a real id.

Message-IDs are stored **with** their angle brackets, because that's the form
`In-Reply-To` and `References` carry.

## Threading (`Ingest::Threader`)

Three strategies, strongest first:

1. **`In-Reply-To`** → look up `messages.message_id`, take that message's ticket.
2. **`References`**, walked **backwards** (newest ancestor first), so a reply
   lands on the nearest ancestor Spool knows about. Unknown ids in the chain are
   skipped rather than fatal.
3. **`[#123]` subject tag** — last resort, for clients that drop both headers
   (webmail after a forward-to-self is the common case).

The first two match on Message-IDs, which Spool generated and nobody can guess,
so a hit is proof. The third matches on a number a human can read off a subject
line and retype, so it carries an extra check: **the ticket's customer must
match the sender.** Without it, anyone quoting a forwarded email would append
themselves to a stranger's ticket. A mismatch opens a new ticket instead —
an agent can see that and merge it mentally, which is the safe direction to
fail.

No match at all opens a new ticket, with `Re:`/`Fwd:` prefixes and any `[#123]`
tag stripped from the subject so the title reads cleanly.

## MIME splitting (`Ingest::MimeSplitter`)

Depth-first walk of the part tree.

- A part with a filename, or a `Content-Disposition` of `attachment`, or
  `inline` with a `Content-ID`, becomes an **attachment**.
- `text/plain` and `text/html` parts become **body**. Multiple parts of the same
  type are concatenated rather than replaced — a forwarded chain or a
  separately-parted signature would otherwise be silently truncated to its last
  fragment.
- Anything else (`application/*`, an image with no disposition) becomes an
  attachment, since it certainly isn't body text.
- A single part over `MAX_INLINE_BODY_BYTES` (2 MB) becomes an attachment
  whatever it claims to be.

### `body_blob` holds JSON, not a bare string

A message legitimately has both a `text/plain` and a `text/html` rendering, and
discarding either loses something: the HTML is what the customer actually saw,
the plain text is what quotes and searches cleanly. So `body_blob` holds
`{"text": …, "html": …}` — the cheapest container that keeps them
distinguishable, and it compresses to nothing next to the body itself.

Every row is written by `MimeSplitter`, so the format is guaranteed. Views
should use `Message#body_text` / `#body_html` / `#body_for_display`, never
`#body` directly.

### Charsets

`part.body.decoded` undoes the transfer encoding but returns bytes still in the
part's own charset. `MimeSplitter#decode_text` transcodes to UTF-8 replacing
anything that doesn't map, and falls back to a scrub on a lying or unknown
charset label. A helpdesk should render a replacement character, not raise while
displaying a customer's email.

## `body_excerpt`

`EmailReplyParser.parse_reply` strips the quoted history. This is what the
ticket list shows and what FTS5 indexes.

The **full body is kept intact** in `body_blob`. Do not "optimise" this by
storing only the stripped reply: customers top-post inside quoted text, and you
will need the original.

For an HTML-only message, `Ingest::Inbound.html_to_text` produces something
searchable. It is deliberately crude — its only job is to feed `body_excerpt`.
The HTML itself is preserved and is what gets rendered.

## `raw_size`

The uncompressed byte size of exactly what the two blobs hold, so that

```sql
SELECT SUM(raw_size), SUM(LENGTH(headers_blob) + LENGTH(body_blob)) FROM messages;
```

measures the real compression ratio on the real corpus. See
[compression.md](compression.md).

## Swapping the transport

The consumer (`Ingest::InboundConsumer`) is four lines of real work: base64-decode
the job body, call `Ingest::Inbound.ingest`. Base64 because a JSON string can't
carry arbitrary 8-bit MIME bytes intact.

To move to a provider webhook, write a controller that verifies the provider's
signature and calls `Ingest::Inbound.ingest(request.body.read, source: "mailgun")`.
Nothing in this document changes. That was the point of the boundary.

## Testing

`test/services/ingest/inbound_test.rb` drives every path from `.eml` fixtures in
`test/fixtures/files/emails/`. No IMAP, no tuber, no HTTP.

Covered: new ticket, all three threading strategies, the subject-tag customer
mismatch, reopening a closed ticket, each rejection rule, self-sent echo,
duplicate delivery, missing `Message-ID`, multipart with inline and regular
attachments, cross-message attachment dedup, HTML-only, ISO-8859-1 with an
encoded-word subject, quote stripping, and FTS5 round-trip.

**Get this correct before putting a live mailbox in the loop.**

Adding a case is: drop an `.eml` in the fixtures directory, call `ingest(:name)`.
